# 02주차 3교시. 내 노트북의 한계를 직접 찾아내기

**오늘 할 일** — 스레드 수를 1 → 2 → 4 → 8로 늘려 가며 추론 시간을 재고, **어느 지점에서 더 이상 빨라지지 않는지**를 각자 찾아낸다. 1·2교시에서 말로 들은 Memory Wall이 내 노트북에서 그대로 재현되는 것을 눈으로 확인하는 시간이다.

> 준비물: 1주차 실습 환경(`odai` 가상환경, `onnxruntime`, `mobilenetv2.onnx`). 없으면 1주차 3교시 3.1을 먼저 수행한다. **보드도 GPU도 필요 없다.**

오늘의 목표는 "빠르게 만들기"가 아니다. **내 기기의 상한을 알아내는 것**이다. 상한을 모르면 최적화를 어디서 멈춰야 할지도 알 수 없다.

---

## 3.1 내 기기는 무엇을 쓸 수 있나 (12분)

1주차 과제였던 `get_available_providers()`를, 이번엔 **하드웨어 관점**으로 다시 읽는다.

```python
import onnxruntime as ort, os
print("실행 공급자:", ort.get_available_providers())
print("논리 코어 수:", os.cpu_count())
```

이 목록이 곧 **1·2교시에서 배운 이기종 컴퓨팅의 소프트웨어 창구**다. 같은 모델을 칩 안의 어느 유닛으로 보낼지가 여기서 갈린다.

| 실행 공급자(Execution Provider) | 실제로 어느 하드웨어인가 |
|------------------------------|------------------|
| `CPUExecutionProvider` | CPU (기본, 어디서나) |
| `CUDAExecutionProvider` | NVIDIA GPU (젯슨, 데스크톱 GPU) |
| `CoreMLExecutionProvider` | Apple Neural Engine / GPU (macOS·iOS) |
| `NnapiExecutionProvider` | 안드로이드 NPU/DSP (모바일 빌드) |
| `QNNExecutionProvider` | Qualcomm NPU(Hexagon) |

> **주의할 것** — 1주차에서 이 목록을 "이 컴퓨터가 어떤 장치로 돌릴 수 있는지"라고 소개했는데, 이제 한 걸음 더 정확히 하자. 이 목록은 "내 기기에 달린 하드웨어"가 아니라 **"설치된 빌드가 지원하는 공급자"** 다. 노트북 CPU 빌드에서는 보통 `CPUExecutionProvider` 하나만 보인다. NPU가 달린 폰이어도 `onnxruntime` 데스크톱 빌드에는 당연히 안 나온다.

`os.cpu_count()`가 알려주는 것은 **논리 코어** 수다. 하이퍼스레딩이 켜져 있으면 물리 코어의 2배로 나온다. 이 구분이 3.2에서 중요해진다.

## 3.2 스레드를 늘리면 정말 빨라질까 (23분)

이제 본 실험이다. **`intra_op_num_threads`** 는 "연산 하나를 몇 갈래로 쪼개서 돌릴까"를 정하는 값이다. 이것을 바꿔 가며 지연을 잰다.

```python
import time, os, numpy as np, onnxruntime as ort

def bench(num_threads, runs=30):
    so = ort.SessionOptions()
    so.intra_op_num_threads = num_threads          # 연산 하나를 몇 갈래로 쪼개 돌릴지
    sess = ort.InferenceSession("mobilenetv2.onnx", sess_options=so,
                                providers=["CPUExecutionProvider"])
    name = sess.get_inputs()[0].name
    x = np.random.rand(1, 3, 224, 224).astype(np.float32)
    sess.run(None, {name: x})                       # 워밍업 (1주차 원칙 ①)
    s = []
    for _ in range(runs):
        t0 = time.perf_counter()
        sess.run(None, {name: x})
        s.append((time.perf_counter() - t0) * 1000)
    return np.mean(s), np.std(s)

print(f"내 기기의 논리 코어 수: {os.cpu_count()}\n")
base = None
for n in [1, 2, 4, 8]:
    m, sd = bench(n)
    if base is None: base = m
    print(f"threads={n:>2} : {m:6.1f} ms  ±{sd:4.1f}   ({base/m:.2f}배)")
```

**실제로 돌린 결과 하나를 보자.** 아래는 논리 코어가 **2개**인 리눅스 서버에서 이 코드를 그대로 실행한 값이다.

```
내 기기의 논리 코어 수: 2

threads= 1 :    9.1 ms  ± 0.5   (1.00배)
threads= 2 :    4.8 ms  ± 0.4   (1.89배)
threads= 4 :   11.4 ms  ± 3.0   (0.80배)
threads= 8 :   37.8 ms  ± 6.5   (0.24배)
```

읽을 것이 세 가지 있다.

**① 코어 수까지는 거의 그대로 빨라진다** — 2개 코어에 2스레드를 주니 1.89배. 이론상 최대인 2배에 거의 닿았다.

**② 코어 수를 넘기면 오히려 느려진다** — 4스레드에서 **1스레드보다도 느려졌다**(0.80배). 8스레드에서는 1스레드의 **4분의 1 속도**다. 코어는 2개뿐인데 8명이 달려들어 서로 자리를 뺏느라 일을 못 한 것이다.

**③ 그리고 값이 들쭉날쭉해진다** — 표준편차를 보라. 0.5 → 0.4 → **3.0 → 6.5**. 느려진 것도 문제지만, **얼마나 걸릴지 예측할 수 없게 된 것**이 더 큰 문제다. 1주차에서 자율주행이 네트워크를 못 믿는 이유로 들었던 그 이야기 — "평균이 아니라 튀는 값이 중요하다" — 가 이번엔 **기기 안에서** 재현된 것이다.

![스레드 수에 따른 CPU 추론 지연(예시) — 늘어날수록 빨라지다가, 물리 코어 수를 넘기면 오버헤드로 다시 느려진다](../assets/w02_p3_threads_bench_06.png)

> **여러분의 숫자는 다를 것이다.** 코어가 8개인 노트북이라면 꺾이는 지점이 8 근처일 것이다. 중요한 건 값이 아니라 **"내 기기에서는 어디서 꺾이는가"** 다. 가능하면 `os.cpu_count()`까지, 그리고 그 두 배까지 재 보라.

## 3.3 꺾이는 지점의 정체 (10분)

꺾이는 이유는 사실 **두 가지가 겹쳐** 있다. 구분해서 보는 것이 오늘의 핵심이다.

**첫째, 코어 경합** — 코어보다 스레드가 많으면 운영체제가 번갈아 태워야 한다. 그 전환 비용이 병렬화 이득을 잡아먹는다. 위 결과의 4·8스레드가 이것이다. 이건 **코어 수를 넘기는 순간** 나타난다.

**둘째, 메모리 대역폭** — 이쪽이 더 근본적이다. 코어를 아무리 정확히 맞춰 줘도, 코어들이 동시에 데이터를 요구하면 **메모리가 대 주지 못한다.** 1교시의 Memory Wall이 바로 이것이고, 코어 수를 넘기기 전에도 이미 작동하고 있다. 코어 8개짜리 노트북에서 8스레드를 줬는데 8배가 아니라 4~5배쯤에서 그치는 경험을 하게 될 텐데, 그 차이가 대역폭 몫이다.

**두 논증을 순서대로 세워 보자.** 라이브러리 없이 산수만 하면 된다.

**(가) 데이터 이동이 지배적 비용이다 — 에너지로 확인**

```python
params = 3_504_872          # MobileNetV2 파라미터 수
macs   = 300_000_000        # 추론 1회 곱셈-덧셈 횟수 (대략)

e_dram = params * 640       # 가중치를 DRAM에서 한 번씩만 읽는다면 (pJ)
e_mult = macs   * 3.7       # 곱셈 전체 (pJ)

print(f"가중치 읽기 : {e_dram/1e9:5.2f} mJ")
print(f"곱셈 전체   : {e_mult/1e9:5.2f} mJ")
print(f"→ 데이터 이동이 계산의 {e_dram/e_mult:.1f}배")
```

```
가중치 읽기 :  2.24 mJ
곱셈 전체   :  1.11 mJ
→ 데이터 이동이 계산의 2.0배
```

**가장 낙관적인 가정에서도 데이터를 나르는 쪽이 2배 비싸다.**

다만 에너지가 비싸다는 것만으로 "그래서 느리다"가 곧바로 따라오지는 않는다. 시간 이야기는 따로 세워야 한다.

**(나) 그래서 대역폭이 먼저 막힌다 — 시간으로 확인**

```python
bytes_w = params * 4                  # FP32 가중치 (바이트)
t_ms    = 4.8                         # 위 실측에서 가장 빨랐던 값

print(f"가중치 1회 읽기량 : {bytes_w/1e6:.1f} MB")
print(f"필요한 대역폭     : {bytes_w/1e6/(t_ms/1000)/1000:.1f} GB/s  (가중치만)")
```

```
가중치 1회 읽기량 : 14.0 MB
필요한 대역폭     : 2.9 GB/s  (가중치만)
```

4.8 ms 안에 추론을 끝내려면 가중치만으로도 초당 **2.9 GB**를 실어 날라야 한다. 활성값까지 더하면 더 늘어난다. **코어를 늘리면 곱셈은 나눠 지지만 이 14 MB는 그대로다.** 여러 코어가 같은 메모리 통로를 나눠 쓰는 순간, 바로 여기서 막힌다.

> **[더 깊이 — 선택]** 병렬화로 얻을 수 있는 최대 속도 향상은 **암달의 법칙(Amdahl's Law)** 으로 위가 막힌다. 병렬화 가능한 비율을 $p$, 코어 수를 $n$이라 하면 최대 속도 향상은 $1/((1-p) + p/n)$ 이다. 위 실측의 2스레드 1.89배를 이 식에 넣으면 $p \approx 0.94$ — 즉 6%가량은 어떻게 해도 순차 실행이라는 뜻이다. 여기에 (나)의 대역폭 상한이 겹치므로, 실제 곡선은 암달 곡선보다 **더 일찍 꺾인다.** 두 상한 중 어느 쪽이 먼저 걸리는지를 구분하는 것이 11주차 프로파일링의 출발점이다.

> **한 줄 정리:** "많은 코어 = 빠름"은 틀렸다. **하드웨어(코어 수와 메모리 대역폭)가 상한을 정하고**, 그 상한은 각자 측정해서 알아내는 수밖에 없다.

## 3.4 과제 (5분 안내)

**1~2쪽**이면 충분하다.

1. **스레드-지연 곡선** — 본인 기기에서 `threads = 1, 2, 4, 8`(가능하면 `os.cpu_count()`와 그 2배까지) 측정해 **평균과 표준편차**를 표로 제출한다. 그래프를 그리고 **꺾이는 지점을 표시**한다.
2. **꺾이는 지점 해석** — 그 지점이 `os.cpu_count()`와 어떤 관계인지 쓴다. 그리고 **표준편차가 어떻게 변했는지**도 함께 보고한다(이게 왜 중요한지 1주차와 연결해 두 문장).
3. **공급자 해석** — 본인 기기의 `get_available_providers()` 결과를 캡처하고, 각 공급자가 어느 하드웨어에 매핑되는지 3.1 표로 설명한다. GPU/NPU 공급자가 없다면 **왜 없는지**도 쓴다.
4. **에너지 산수** — 3.3의 계산을 본인 관심 모델의 파라미터 수로 바꿔 다시 하고, 데이터 이동이 계산의 몇 배인지 구한다. 그 결과가 2교시의 타일링과 어떻게 연결되는지 3~4문장.
5. **다음 주 예습** — 3주차(추론 엔진)에서는 오늘 본 공급자에게 연산을 **실제로 위임하는** 장치를 다룬다. 이 위임 장치를 **Delegate**라 부른다. `onnxruntime`이 그래프를 어떻게 최적화하는지 미리 검색해 온다.

> 교수님을 위한 Tip: 이 실습은 **각자 다른 숫자가 나오는 것이 정상이고, 그게 오히려 좋습니다.** 코어 수가 다른 학생들의 결과를 칠판에 모아 놓고 "꺾이는 지점"과 `cpu_count()`를 나란히 적으면, 한 사람의 실험이 **여러 하드웨어에 걸친 관찰**로 바뀝니다.
>
> 젯슨 등 CUDA 보드가 있으면 `providers=["CUDAExecutionProvider"]`로 같은 벤치를 돌려 비교 데모를 보여주면 효과가 큽니다. **없어도 실습은 완결됩니다.** 폰에서 같은 실험을 해 보고 싶은 팀에는 [부록 A](appendix-a-phone-profiling.md)를 안내하세요 — `--num_threads`를 바꿔 가며 같은 곡선을 그릴 수 있고, 14주차 캡스톤 준비도 겸하게 됩니다.

### 3교시 정리
- 실행 공급자 목록을 **하드웨어 매핑**으로 해석했다 — 이기종 컴퓨팅의 소프트웨어 창구.
- 스레드를 늘리면 코어 수까지는 빨라지지만, **넘기면 느려지고 값이 들쭉날쭉해진다**는 것을 직접 측정했다.
- 꺾이는 이유가 **코어 경합**과 **메모리 대역폭** 둘로 나뉜다는 것을 구분했다.
- 에너지로는 **데이터 이동이 계산의 2배**, 시간으로는 **가중치만 초당 2.9 GB**가 필요하다는 것을 내 모델에서 계산했다.
- 다음 주에는 이 하드웨어를 실제로 부리는 소프트웨어, **추론 엔진**으로 넘어간다.
